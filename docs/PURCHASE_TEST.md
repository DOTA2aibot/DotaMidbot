# T017 — закупка MIDBOT v0.2: проверка

Изменение — кандидат на игровой тест; задача ещё не Done. Owner: Артём / artem-esenkov-iu-study, reviewer: Олег/Kimi. Основание — [Issue #17](https://github.com/DOTA2aibot/DotaMidbot/issues/17). Ветку не сливать до проверки игрового AC и ревью.

## Что исправлено

- Используется `ActionImmediate_PurchaseItem`; следующий компонент удаляется только при результате `PURCHASE_ITEM_SUCCESS`. `nil` или любой отказ оставляют очередь на месте.
- Готовые вещи разбираются через `GetItemComponents`, без зашитых рецептов и цен. Для альтернатив берётся первый рецепт; его пригодность SF и форму данных проверить в клиенте.
- Уже имеющиеся предметы в inventory/backpack/stash и на собственном курьере учитываются при создании плана. Чужой курьер исключается. Один имеющийся компонент не покрывает две одинаковые позиции рецепта.
- План компонентов сохраняется между попытками: оплаченная часть не покупается снова только потому, что доставка или автосборка ещё не завершились.
- Попытки ограничены интервалом 0.5 игровой секунды. Причины отказов и результат пишутся с префиксом `[MIDBOT purchase]`; одинаковые соседние сообщения не повторяются.
- Список итоговых вещей сохранён. Версия игрового кода повышена до v0.2; логика способностей и выбор героев не меняются.

`plan_complete` означает, что список покупок/имеющихся компонентов исчерпан, **не** подтверждает доставку или сборку. Это проверяется по инвентарю в игре.

## Выполненная автоматическая проверка

На машине GPT использован Python 3.13 + lupa 2.8 с реальным Lua 5.1 runtime. Прогоняет именно Lua-файл закупки, Dota API заменён mock. Проверены 17 сценариев: отказы, nil, недостаток золота, ограничение частоты, вложенные рецепты, повторяющиеся части, stash/курьеры, повторная попытка в середине рецепта, inventory/backpack, некорректные/циклические рецепты и завершение очереди.

Запуск из корня репозитория при установленном Lua 5.1:

```text
lua tests/purchase/test_purchase.lua
```

Альтернатива для разработчика с Python (не требуется для игрового теста):

```text
python -m venv .venv
.venv\Scripts\python -m pip install lupa==2.8
.venv\Scripts\python tests/purchase/run_tests.py
```

Это не доказывает корректность Dota API, текущих рецептов или доставки. Fixture-рецепты синтетические.

Регрессионная проверка на исходном v0.1 действительно падает на первом тесте: после отказа следующая попытка — `item_wraith_band` вместо повторного `item_tango`. На кандидате тот же тест проходит. Дополнительные тесты не требуют запуска игры или платных ресурсов.

## Проверки reviewer перед принятием

| Случай | Что должно произойти | Свидетельство |
|---|---|---|
| Недостаточно золота | Нет списания/пропуска, ожидание нужного компонента | Золото, следующий предмет |
| Отказ магазина/нет места/нет stock | Тот же компонент повторяется после снятия причины | Код отказа → код успеха, очередь |
| Составная вещь | Покупаются части актуального рецепта, вещь собирается после доставки | Лог + inventory/stash |
| Компонент уже на своём курьере | Не покупается лишняя копия при создании плана | Снимок груза + лог |
| Повторяющиеся части рецепта | Покупается нужное число, а не одна часть вместо двух | Рецепт + покупки |
| Секретная лавка | Нет ложного продвижения при недоступности; после доступа успешная покупка | Соответствующий run |

Для отказа достаточно одного воспроизводимого безопасного случая в тестовом лобби; точный способ воспроизведения зависит от проверенного T003. Не вводить непроверенные консольные команды из чата. Длинная серия матчей/обучение не нужны.

## Известные границы

- Новый код **не управляет курьером**, не ведёт героя к секретной лавке и не продаёт вещи. Если штатная логика не обеспечивает доступ/доставку или инвентарь забит, очередь честно ждёт. Для автономного late-game это может потребовать отдельной задачи после run.
- Нет восстановления очереди после hot reload, продажи/потери предметов и ручных вмешательств в инвентарь во время уже построенного плана. Тест начинать новым матчем; данные об уже оплаченных частях живут только в Lua-сессии.
- Возможные API/рецепты/доступность предметов текущего build требуют проверки. Выбор первого альтернативного рецепта не является оптимизацией билда.
- Не использовать тестовый успех как утверждение, что весь T017 завершён. Нужны игровой результат, независимое ревью, merge и общий DoD.
