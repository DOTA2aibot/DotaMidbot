# Загрузка и настройка GitHub

Для DotaMidbot: 18 Issues уже созданы, документы опубликованы в ветке gpt/project-coordination через PR. Merge и независимое ревью ещё нужны; labels и branch protection не включались. Дальнейший текст — инструкция для настройки, а не подтверждение выполненных действий. Сначала определить свой репозиторий и не перезаписывать уже начатый код.

## Первая загрузка

1. Распаковать ZIP. В корень репозитория переносить **содержимое** `dota2-ai-project/`, чтобы README.md и `.github/` оказались в корне, а не на уровень глубже.
2. Если репозиторий новый, загрузить файлы первым commit. Если он уже существует, создать отдельную ветку и PR, сопоставить одноимённые документы, сохранить полезное из старых файлов. Не загружать сам ZIP как основной набор документации.
3. Проверить наличие `.github/ISSUE_TEMPLATE/` и `.github/PULL_REQUEST_TEMPLATE.md`: некоторые файловые диалоги скрывают папки с точкой. Веб-интерфейс должен показать шаблоны при создании новой Issue после merge в default branch.
4. Включить Issues; пригласить второго человека. Репозиторий, аккаунты и доступы выбираются самими авторами.
5. Согласовать T001 и T002. Этот комплект не создаёт GitHub Issues, project board, labels, CODEOWNERS или branch protection.

## Ветка main и ревью

Если тариф/видимость репозитория поддерживает необходимые правила, настроить ruleset для default branch: изменения через PR, одно одобрение другого человека, снятие устаревшего одобрения после новых commit, разрешение обсуждений перед merge, запрет force-push и удаления ветки. Доступные опции проверить в фактических настройках; наличие документа не означает, что защита включена.

Пока CI нет, не включать несуществующие required checks. После T015 требовать только реально работающие offline-проверки. Игровые проверки подтверждаются артефактами в PR; GitHub-hosted runner с Dota здесь не предполагается.

Если автоматическое принуждение недоступно, записать это в T002 и соблюдать то же правило вручную: автор не вливает собственный PR без согласия второго. Прямые push в main после bootstrap не использовать.

CODEOWNERS добавлять только после появления реальных аккаунтов и подтверждения ролей. В этом наборе его нет, чтобы фиктивные имена не выглядели работающим автоматическим review routing. Если добавите — согласуйте с таблицей областей TEAM_WORKFLOW.

## Labels

Перед созданием Issues по шаблонам вручную создать:

| Группа | Значения |
|---|---|
| Тип | `type:task`, `type:bug`, `type:decision` |
| Состояние | `state:inbox`, `state:ready`, `state:in-progress`, `state:review`, `state:blocked`, `state:done`, `state:cancelled` |
| Приоритет | `priority:P0`, `priority:P1`, `priority:P2` |
| Область | `area:game`, `area:data`, `area:ml`, `area:process`, `area:contracts` |

Пока labels не созданы, использовать поле `State:` в теле каждой Issue. После настройки на Issue ровно один state label; исключить расхождение поля и label. Milestones M0–M3 можно создать после согласования roadmap. Сроки не ставить без совместной оценки.

Project board необязателен. Если используете, его state должен быть синхронизирован с Issue; назначьте labels каноническими, board — производным представлением. Не вести третью независимую таблицу состояния.

## Однократная миграция BACKLOG → ISSUES (T014)

1. На короткое совместное окно приостановить новые claims и смену статусов; действующие owners сохраняются.
2. Создать по одной Issue на каждую T-ID из backlog: переносить AC, deps, owner/state, разрешённые пути и handoff. В заголовке сохранить T-ID; GitHub номер не подставлять вместо него.
3. В BACKLOG заменить оперативную таблицу индексом `T-ID → Issue URL`. Не оставлять вторую актуализируемую колонку owner/state.
4. Проверить с коллегой все ссылки, dependencies, открытые claims и отсутствие дублей. Если перенос неполный, Task mode остаётся BACKLOG; Issues пока считаются черновиками миграции.
5. Одним PR поменять Task mode и canonical task registry в STATUS, заменить реестр в BACKLOG индексом. После merge возобновить работу в Issues по процедуре подтверждённого claim.
6. В Issues owner = один human assignee; assistant/session, branch и paths — в claim/handoff. Closed Issue недостаточно для Done без PR и свидетельств DoD.

## Проверить после настройки

- [ ] Оба человека читают/изменяют репозиторий и могут ревьюить PR.
- [ ] README и локальные ссылки открываются на GitHub.
- [ ] Доступны 3 Issue templates и PR template.
- [ ] Labels созданы; ограничения защиты ветки документированы.
- [ ] A/B заменены реальными назначениями в TEAM_WORKFLOW.
- [ ] Task mode однозначен; не появились конкурирующие реестры.
- [ ] LICENSE выбран авторами отдельно; код друга не потерян.
