# EVALUATION

Протокол сравнения версий бота. **Сейчас результатов нет.** Первые реальные команды, конфигурации и отчёты появятся после T003–T010. Пороговые значения ниже — предложенные критерии ранних этапов, не измерения существующего бота.

## Три разных проверки

1. **Работоспособность M1:** 3 последовательных run по 10 игровых минут, без необработанной ошибки нашего кода, с подтверждённым движением, попытками добивания и хотя бы одним last-hit в серии; отдельно сценарий retreat.
2. **Характеристика baseline M2:** минимум 10 валидных run. Это небольшой стартовый набор, достаточный для описательной сводки, но не для громких статистических выводов.
3. **Сравнение candidate M3:** заранее замороженный протокол и held-out сценарии, та же длительность и условия, минимум 10 run на вариант; размер увеличивается, если вариативность не позволяет сделать вывод.

## До серии

Зафиксировать в evaluation-config: build/patch игры, code SHA и clean/dirty, policy/config/schema version, герой, сторона, соперник и его сложность/версия, сценарий, начальные условия, длительность, количество повторов, доступный seed, основные метрики, правила исключения и promotion thresholds.

Герой уже Shadow Fiend; соперника и остальные условия фиксирует T004 по результатам T003. Если deterministic seed недоступен, записать `unavailable`, не обещать побитовую повторяемость. Для baseline/candidate чередовать порядок запусков, балансировать стороны там, где это проверено. Изменение патча, героя или сложности создаёт отдельную серию.

## Метрики

| Метрика | Определение | Доступность |
|---|---|---|
| LH@10 | Last hits контролируемого героя на game_time 600 s | Проверить счётчик в T003 |
| Deaths@10 | Смерти героя в первые 600 игровых секунд | Проверить источник событий |
| Gold/XP delta | Разница показаний между фиксированными t0/t1 | Только при доступности; не называть автоматически GPM/XPM |
| Runtime errors/run | Необработанные ошибки нашего runtime за run | Лог собственного кода |
| Invalid-action rate | Число rejected action / число proposed action | Считать нулевой denominator как N/A |
| Fallback rate | Решения через fallback / все решения | Причины отдельно |
| Decision latency p50/p95 | От наблюдения до submission, monotonic wall-clock | Только если путь измерения проверен |
| Run completion | Достигнут лимит / матч закончился / runtime crash / external failure | Manifest |

Недоступная метрика — `N/A` с причиной, не 0. Если LH@10 недоступна, до сбора серии T004 согласует альтернативную основную метрику и новую версию протокола. Нельзя выбирать её после просмотра результата candidate.

## Валидность и исключения

- Валидный 10-минутный run достигает game_time 600 s и содержит требуемую телеметрию. Интервал pregame не входит в 10 минут.
- Crash нашего кода и досрочная игровая потеря не исчезают из отчёта: отдельно failure count, фактическая длительность и доступные частичные метрики. Не экстраполировать LH@10.
- Внешний сбой (клиент не стартовал, обновление игры, отключение питания) может исключаться из основной сводки только по заранее принятому правилу. ID и причина остаются в полном реестре.
- Потеря телеметрии делает run неполным, но не оправдывает скрытие ошибки логгера. Отдельно считать missing-data rate.
- Запрещено оставлять только удачные игры, лучшие seeds или checkpoint, выбранный на финальном held-out наборе.

## Run artifacts

Рекомендуемая структура внешней папки данных; это целевой формат, не созданные файлы:

```text
run-id/
  manifest.json
  decisions.jsonl
  summary.json
  runtime.log
```

Manifest соответствует ARCHITECTURE; дополнительно `termination_reason`, число пропущенных событий, data/config hashes и версия анализатора. Ссылки и контрольные суммы записываются в отчёте. Сырые данные/веса не кладутся в обычный Git; маленькие fixtures можно. Хранилище и срок хранения выбираются в T006, доступ должен быть у обоих людей.

## ML-эксперимент

Train/validation/test разделяются по полным match/run, при необходимости по сценариям. Соседние кадры одного матча не попадают в разные split. Нормализация учится только на train. Features и labels должны быть доступны в момент предполагаемого решения; итог будущего события допустим как label, но не как feature.

Baseline и candidate используют одинаковые доступные наблюдения и action-space. В M3 меняется один компонент. Сохранить dataset manifest/hash, код подготовки, seed где доступен, library versions, checkpoint metadata, бюджет CPU/GPU/wall-time и фактическую стоимость сбора опыта.

T010 до candidate-оценки заполняет: основная метрика, минимальный полезный эффект, допустимый предел deaths/fallback/latency/error rate и метод оценки неопределённости. Пример гипотезы «увеличить LH@10» сам по себе не является критерием promotion. Пока численные thresholds не согласованы, можно исследовать, но нельзя продвигать модель.

## Решение по candidate

Отчёт содержит все run ID, число валидных/неполных/неуспешных run, распределения метрик (как минимум median и min/max), сравнение с baseline, ограничения и стоимость. При уместности добавить интервалы неопределённости; не объявлять статистическую значимость по одной разнице средних.

Promote разрешён, когда заранее принятый threshold пройден, guardrails соблюдены, данные воспроизводимы и второй участник согласен. Иначе iterate/reject/inconclusive. Baseline-tag сохраняется для rollback. При смене протокола проводить новую серию; результаты разных протоколов не смешивать.
