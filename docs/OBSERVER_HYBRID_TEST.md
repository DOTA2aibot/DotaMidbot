## Выбор после сравнения PR38 и PR39

По поручению Artem сравнили обе версии и оставили совместимый объединённый вариант в PR39. Это не две конкурирующие модели управления.

| Часть | Выбранный вариант | Причина |
|---|---|---|
| Основной сбор статистики | Observer из PR39: снимки 1Hz и структурированные события | Работает без modifier-diag; состояние, решения и свидетельства действий можно разбирать отчётом |
| Краткая диагностика | Stats из PR38 Олега (Kimi) сохранены | Полезны для ручной проверки; включаются вместе с modifier-diag, раз в 3 секунды |
| Атаки и перемещения | Прежний Valve controller в valve_play | Активная замена атак не прошла игровой A/B и пользователем отложена |
| Выбор attack/raze и хайграунд | Shadow из PR39, без приказов | Сохраняет признаки и рекомендации для анализа, не приписывает им действия Valve |
| Новая постановка вардов | Только отдельный valve_wards | Меняет действия; проверяется после observer-only, не одновременно |

Оба PR направлены в main. Порядок принятия при неизменном head38: сначала PR38, затем PR39; переносить ветки или копировать файлы вручную не требуется. Уже собранный observer-only ZIP из PR39 включает оба изменения и пригоден для локального теста до merge. Независимое ревью, новый игровой запуск и оценка стоимости наблюдателя остаются обязательными для завершения задачи.

## Что меняется в игре

| Профиль | Перемещения и AA | Способности/покупки | Новые приказы |
|---|---|---|---|
| valve_play, default | Valve | Прежние правила проекта, с журналом | **Нет**: observer/shadow только читают |
| valve_wards, отдельный opt-in | Valve | Те же правила | Только условная постановка варда в существующей дальности |
| lane_probe | Прежний отдельный runtime | С прежним handoff | Прежний диагностический режим; observer по умолчанию выключен |

По уточнению пользователя активная замена обычных атак и выбора engine modes отложена. Собственная shadow-политика предлагает, а не исполняет attack/raze; нельзя объявлять её источником успешного native фарма. Пороговые правила существующих способностей и покупок не переписаны, изменены только защищённые hooks и журнал уже выдаваемых кастов/доворотов. Установленная рабочая v0.3.2 остаётся без изменений до отдельной установки кандидата.

## Данные и ограничения

Новый префикс консоли: **[MIDBOT observe]**. Снимок1Hz: LH/deny/kill/death, уровень, HP/мана, позиция, активный mode/action, собственный attack record/target, ресурсы/слоты предметов0–14, собственные уровни/CD/мана способностей, видимые enemy heroes и lane creeps, HP/броня/evasion/modifiers/высота и damage query estimates. Радиус1400, максимум16 целей; truncation обозначен. Скрытые ресурсы героя противника не читаются, чужие CD не запрашиваются. Неизвестность не заменяется нулём. Пустая Lua-коллекция может сериализоваться как {}; это не отсутствующее API.

Каждая запись имеет schema/version/profile/controller/source_revision, run_id, seq, observation_id и игровое time. Сборщик ZIP встраивает заявленный revision в профиль, а hashes manifest позволяют проверить реальные байты; сам packager не удостоверяет происхождение переданного revision. Shadow-решение ссылается на seq своего snapshot, сохраняет все25 action-mask IDs, candidates/features/reasons и executed=false. Неисполняемые combo IDs остаются masked. Это подмножество исполнителя, не новая упрощённая обученная модель.

Дополнительный read-only опрос attack evidence ограничен0.1с и одной текущей целью. `attack_release_observed` требует изменения attack record и нового близкого собственного атакующего снаряда; при одном timestamp пишется `attack_record_changed`. Это нижняя оценка наблюдённых выпусков, **не полный счётчик атак, промахов или попаданий**. Clock GetLastAttackTime не смешивается вычитанием с DotaTime.

Собственные Action_UseAbility и существующий face move получают action_submitted. Рост CD и расход маны могут дать cast_consumption_observed; regen/пропущенная фаза/недоступные поля оставляют outcome unknown. Ни submission, ни release, ни расход ресурсов не подтверждают hit/kill. Прирост LH/deny/kill в snapshot — interval-only, без причинного присвоения рекомендации. reward_status=not_defined. Это ещё не готовый RL dataset.

Observer/shadow и его sink защищены: ошибка не прекращает прежний ability callback. Ненулевая стоимость сбора/печати возможна и должна измеряться в игре; offline Lua mocks не доказывают FPS. Частоту, радиус, cap и выключение shadow можно менять в observer/config.lua до нового теста. Для полного отключения observer используется observer_enabled=false в профиле; ward executor при этом тоже не запускается.

## Хайграунд

Используется `GetHeightLevel(location)` (optional API), а не визуальная Z. При известном uphill shadow снижает score обычного удара и рассматривает доступный рейз с текущей геометрией, маной/CD и оценкой урона. Неизвестный terrain остаётся unknown. Числовой score не означает процент промаха; balance miss chance не зашит как достоверное число.

Рейз не называется гарантированным добиванием: base GetAbilityDamage/engine incoming-damage query здесь не калибруют стаки, души, shields, nonlinear blocks и движение цели до impact. Собственная продвинутая модель/калибровочные маски T007 сохраняются. Ward vision помогает наблюдать цель, но terrain-level для атаки остаётся прежним. В этой итерации uphill-рекомендация **не меняет реальные касты или удары**.

## Ограниченный тест вардов

Только valve_wards включает executor. Он не вызывает Move/AttackMove/Clear/Attack и не меняет приоритеты режимов. После existing abilities проверяются idle, HP≥70%, отсутствие видимого врага900, известные данные безопасности, район мида и дальность предмета. При движении/замахе/использовании способности/отступлении выдаётся skip, а не отмена команды.

Выбираются проверяемые точки высокого рельефа на противоположной половине мида, в текущей дальности item cast. Нет собственного подхода к точке и нет обещания, что бот обязательно попадёт в такое окно. Видимые вышки и уже установленные allied wards ограничивают выбор. Черезпроходимость выбирается консервативный вариант; это не полный поиск лучших cliff spots и не доказательство фактического обзора. Обе стороны карты нужно проверить в клиенте.

Observer ставится ради обзора. Sentry рассматривается рядом с имеющимся observer ради detection, не как замена обычному vision. Код не расходует все варды в одну покрытую точку. Предметы в backpack/stash только отмечаются; swap/courier/purchase не добавлялись.

Для ward_dispenser применяется только **текущий режим**: mapping GetToggleState на тип не выдумывается и автоматического toggle нет. Первый результат может оказаться sentry; `ward_observed` запишет фактический тип нового nearby ward вместе с расходом заряда. Для полноценного автоматического выбора типа dispenser нужен отдельный подтверждённый probe. Пока нельзя обещать observer vision от любого dispenser cast.

До приказа пишется ward_proposal; при отказе sink экспериментальный приказ не выдаётся. API submission не равен установке. Подтверждение требует расхода заряда и нового nearby ward; отсутствие owner binding помечено отдельно. Timeout — ward_outcome_unknown, а не успех. Interval20с ограничивает повторные попытки.

## Как тестировать

1. Сначала отдельный ZIP **valve_play**, как технический A/B с рабочей v0.3.2: тот же Local Host/All Pick, сложность, фактический roster, соперник и длительность. Сохранить manifest и лог с начала. Корневого mode/bot override в play нет.
2. Первые2–3минуты: SF играет привычно, новые записи появляются примерно1Hz; нет observer WARN/ability ERROR flood, рывков/зависаний и заметного падения производительности. Затем прогон за10:00. Не объявлять shadow-рекомендации реально исполненными.
3. При ухудшении остановить тест и восстановить backup v0.3.2. Не включать принудительный AA-перехват: такого режима в этой сборке нет. Для объективного сравнения нужны повторные одинаковые прогоны, а не один субъективный бой.
4. Только после проверки observer-only отдельно испытать **valve_wards**. Проверить наличие активного ward item, безопасность, mid position и idle window. Если бот не ставит — смотреть ward_skip/ward_suggestion; не заставлять его идти под башню ради теста.
5. Наблюдать тип/место нового варда, изменение заряда и фактический обзор; record ward_observed проверить по кадру. Передать весь игровой log, включая суффикс номера матча. Задержка до подходящего idle window ожидаема.

Сборка:

```powershell
python tools/package_bot.py --profile valve_play --output MIDBOT-v0.3.3-observer.zip
python tools/package_bot.py --profile valve_wards --output MIDBOT-v0.3.3-wards-test.zip
```

Для привязки к опубликованному снимку добавить --revision с полным SHA. Установка — прежний checked installer с backup и полной заменой bots; закрыть Dota, новый матч, без наложения старых файлов.

Отчёт:

```powershell
python tools/observer_report.py "match.log" --outdir report/test-001
```

Получатся REPORT.md, summary.json и telemetry.jsonl. Фильтруются только записи наблюдателя; произвольные network/chat строки не переносятся. Старый лог v0.3.2 не содержит этих записей, поэтому report покажет неизвестную статистику, а не вымышленные нули. Samples после600 секунд подтверждают продолжение наблюдения, а не активную игру. Exact hit rate/kill attribution остаются unknown.

Проверки: tests/laning/run_tests.py и verify_checkouts.py. Они используют Lua5.1 и подставной API; новый игровой запуск, FPS и качество рекомендаций пока не проверены. Профиль установленной игры автоматически не меняется. [ADR0006](adr/0006-observer-shadow.md) — Proposed.
