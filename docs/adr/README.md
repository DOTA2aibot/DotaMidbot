# ADR — журнал решений

ADR (Architecture Decision Record) хранит контекст, выбранный вариант и последствия решения. Номер постоянный, принятую историю не стираем. Новый документ — следующий свободный номер; [шаблон](0000-template.md) не является решением.

**Принятых решений в стартовом наборе нет.** Предложения согласуются в T001 после аудита начатого кода.

## Процесс

1. Создать задачу выбора и Proposed ADR по шаблону. Указать альтернативы, неизвестные и способ проверки.
2. Если нужен spike, провести ограниченный эксперимент с отдельными AC и бюджетом. Наличие документа не доказывает работоспособность выбранной технологии.
3. Оба человека явно подтверждают решение в PR. После этого статус Accepted, дата и ссылка на PR; обновляются ARCHITECTURE и затронутые задачи.
4. Rejected сохраняется с причиной. Accepted заменяется новым ADR: старый помечается Superseded с взаимными ссылками. Косметические уточнения допустимы без изменения смысла.

ADR нужен для игрового маршрута интеграции, контракта producer/consumer, транспорта, training algorithm/framework, важных зависимостей и хранения данных. Локальная функция без изменения интерфейса обычно не требует отдельного ADR.

Не считать ответ AI одобрением людей. Если мнения разошлись, сохраняются baseline и текущий интерфейс; следующий шаг — конкретный проверяемый spike, а не два несовместимых варианта в main.
