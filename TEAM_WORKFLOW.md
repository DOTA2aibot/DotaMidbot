# TEAM_WORKFLOW

## Люди, роли и ответственность

Два человека принимают решения и отвечают за результат. AI-ассистент — инструмент закреплённого человека: он не становится третьим владельцем задачи и не заменяет независимое ревью.

| Роль | Основная область | Предлагаемый участник | GitHub |
|---|---|---|---|
| A | Данные, оценка, исследовательские гипотезы, backlog | Артём / GPT | artem-esenkov-iu-study |
| B | Игровая интеграция, Lua, запуск, базовое поведение | Олег / Kimi | Аккаунт не подтверждён |

Распределение предложено для старта. В T001 оба подтверждают или меняют роли. До этого никто не считается фактически назначенным владельцем. Owner задачи может отличаться от владельца области; это фиксируется явно.

### Владение областями после подтверждения ролей

| Область / будущие пути | Основной reviewer | Дополнительное условие |
|---|---|---|
| `bot/`, `tools/launch/`, сценарии установки | B | A может выполнить инструкцию на своей машине |
| `analysis/`, `experiments/`, `docs/EVALUATION.md` | A | B подтверждает применимость к игре |
| `contracts/`, `ARCHITECTURE.md`, ADR | A и B | Требуется явное согласие обоих |
| `BACKLOG.md`, `STATUS.md`, workflow и AGENTS | A и B | Изменения согласуются через PR |
| `tests/`, `configs/` | Reviewer соответствующего компонента | Контрактные изменения согласуют оба |

Для текущего дерева `hero_selection.lua`, `ability_item_usage_nevermore.lua`, `item_purchase_nevermore.lua` основная игровая область B; точный claim важнее будущих путей `bot/`. Любые параллельные изменения этих файлов согласуются пофайлово.

У пары всегда есть один автор и второй reviewer. Автор области не одобряет собственный PR вместо коллеги. Владение областью означает обязанность разобраться, а не запрет другому её менять.

## Источники истины и разногласия

- BACKLOG или Issues в зависимости от Task mode в STATUS: единственный реестр owner, state, dependencies и claim.
- Принятые ADR: выбранные архитектурные решения; ARCHITECTURE отражает их текущий итог.
- ROADMAP: границы этапов. EVALUATION: протокол сравнения. STATUS: сводка подтверждённых возможностей.
- Исходный код и результаты проверок: свидетельство фактического поведения, но случайная реализация не отменяет контракт.
- Чат, старые планы и память моделей: справочные материалы. Новое предложение переносится в задачу или ADR.

Если код, контракт и ADR расходятся, создать defect/decision task и отметить расхождение. До решения не расширять затронутый интерфейс. Менять договорённость нужно явным PR, а не молча подгонять документы под ошибку.

## Состояния задач

`Inbox → Ready → In progress → Review → Done`; из рабочих состояний возможен `Blocked`, затем возврат после снятия блока. `Cancelled` требует причины. Состояние Blocked сохраняет владельца и reservation до явной передачи.

**DoR (можно брать):** есть T-ID, цель, границы, acceptance criteria, зависимости, кандидат owner, reviewer, разрешённые пути и способ проверки. Зависимости завершены или задача явно допускает автономную подготовку. Ready ещё не резервирует работу.

**WIP:** максимум одна In progress задача на человека, всего две; Blocked также занимает слот, пока не передана или явно приостановлена. Для Review разрешено начать следующую независимую задачу после освобождения путей. Один человек не запускает несколько AI-сессий на одну задачу без явного непересекающегося разделения.

## Claim: как не начать одну задачу вдвоём

### Пока Task mode = BACKLOG

1. Обновить локальную main. Проверить строку задачи и зависимости.
2. Открыть маленький coordination PR: owner = свой GitHub, state = In progress, указать ветку реализации, reviewer, UTC-время начала, session-id и разрешённые пути в карточке задачи.
3. Второй участник проверяет отсутствие пересечения с активной задачей и вливает claim. **Реализация начинается только после merge claim в main.** Черновые локальные заметки допустимы, изменения зарезервированных компонентов — нет.
4. Claims вливаются по одному. Перед merge второй claim проверяется относительно уже обновлённой main; при пересечении правится scope или выбирается другая задача.

Это резервирование через согласованное состояние main, а не надежда на то, что два сообщения разойдутся вовремя. Coordination PR не является доказательством выполнения задачи.

### После Task mode = ISSUES

Пока labels не созданы, канонический state записывается полем `State:` в теле Issue; после настройки labels один state label становится каноническим, поле в теле синхронизируется или удаляется. Project board не создаёт отдельный реестр.

Owner ставит одного human assignee и комментарий `CLAIM Txxx | branch | paths | session | UTC`. Второй участник отвечает `CLAIM CONFIRMED`, проверив актуальные assignee и остальные активные задачи. Только после этого перевод в In progress и реализация. GitHub не гарантирует эксклюзивный claim одним назначением; без подтверждения работа не начинается. Ошибочную двойную заявку решают до начала кода.

### Пересечение и передача

- Две задачи не редактируют один файл одновременно. Разделить по файлам либо выполнять последовательно. Согласование интерфейса — отдельная задача, затем потребители.
- BACKLOG/STATUS изменять маленькими последовательными PR; необходимость обновить общий документ не даёт права перезаписывать чужое состояние.
- Ветка `task/T005-baseline` и worktree/локальный checkout принадлежат конкретной задаче. У двух сессий не должно быть общей рабочей папки с незакоммиченными изменениями.
- Claim не истекает автоматически. На следующей совместной синхронизации уточнить зависшую работу; освободить только явной передачей с сохранением результатов.
- Передача содержит SHA/ветку, изменённые файлы, выполненные проверки, блокеры, next step. Новый owner подтверждает приём в канонической карточке. Старую AI-сессию остановить до передачи путей.

## Работа с PR

1. В одном PR одна задача или её заранее выделенный небольшой шаг.
2. Перед Review: обновить ветку относительно main, проверить diff и чужие изменения, выполнить применимые проверки.
3. Приложить T-ID, описание поведения, команды и фактические результаты, ограничения, handoff; заполнить PR template.
4. Второй человек проверяет требования и свидетельства, затем Approve или конкретные замечания. Для игровых изменений нужна ссылка на run/запись, а не только текст AI.
5. После merge обновить канонический реестр. Done — после merge и выполнения DoD. Если авто-закрытие Issue произошло раньше, вернуть задачу в рабочее состояние.

При недоступности коллеги PR остаётся в Review; можно готовить независимую задачу, но не выдавать самопроверку за согласование. Решения по контрактам, лицензии и архитектуре требуют обоих.

## Общий Definition of Done

- [ ] Выполнены acceptance criteria задачи; scope соответствует claim.
- [ ] Код/документы сохранены в PR и влиты в main после ревью второго человека.
- [ ] Применимые проверки выполнены; указаны команда, среда и результат. Невыполненное обозначено явно.
- [ ] Для поведения есть воспроизводимый сценарий; исправление ошибки проверено на исходном случае.
- [ ] Контракты, конфигурация, инструкции и примеры обновлены при изменении интерфейса.
- [ ] Для архитектурного выбора принят ADR; новый эксперимент не называется принятым решением.
- [ ] Нет секретов, абсолютных путей чужого ПК, крупных run-данных или случайно скопированных внешних файлов.
- [ ] Task state обновлён; STATUS обновлён, если изменились этап или подтверждённые возможности.
- [ ] Сохранён handoff для следующей сессии.

Для документации достаточно проверки ссылок, терминов и согласованности; запуск игры не нужен. Для аналитики нужны sample input и воспроизводимый результат. Для gameplay нужны контрактные проверки и игровой smoke-test. ML оценивается по EVALUATION, а не по одному удачному матчу.

## Ритм двух человек

В начале рабочей сессии: прочитать актуальный реестр, подтвердить claim и разрешённые пути. В конце: состояние, свидетельства, блокеры и следующий шаг в карточке задачи. Раз в неделю, если оба работают: короткая синхронизация по одному общему результату, рискам и двум следующим задачам. Частоту и календарные даты согласовать в T001; заранее обещанных сроков нет.
