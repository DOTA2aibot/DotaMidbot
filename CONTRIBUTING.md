# CONTRIBUTING

Проект ведут два разработчика. Каждый вклад привязан к задаче, одному human owner и проверке второго участника. Подробные правила — [TEAM_WORKFLOW](TEAM_WORKFLOW.md).

## Перед изменением

1. Прочитать STATUS и канонический реестр задач; для AI дополнительно AGENTS и AI_CONTEXT.
2. Выбрать Ready-задачу, согласовать scope и получить подтверждённый claim.
3. Обновить main; создать отдельную ветку `task/Txxx-short-name`. Не работать в общей папке двух AI-сессий.
4. Проверить существующие файлы и аудит: пригодный код не переписывать без причины.

## Изменение

- Небольшие изменения в пределах задачи. Commit message: `T007: handle vanished creep target` или столь же конкретно по-русски.
- Пользовательская документация по-русски, имена кода и полей единообразны. Не менять стиль всего проекта ради одной функции.
- Добавлять зависимости только при необходимости; записать версии и причину. Контракты/алгоритмы/транспорт меняются через ADR и согласие обоих.
- Не коммитить токены, `.env`, локальные Steam-пути, игровые binaries, большие логи, datasets и checkpoints. Sample fixtures должны быть малыми и очищенными.
- Не переносить внешние код/картинки/промпты без проверки происхождения и лицензии. Ссылаться на источник идеи и описывать собственное решение отдельно.

## Проверка

Есть Lua-исходники прототипа, но общей проверенной команды сборки/тестов и подтверждённого успешного run пока нет. Не использовать придуманные команды из AI-ответа. После T015 подтверждённые команды будут в `docs/DEVELOPMENT.md`.

| Тип изменения | Минимальное свидетельство |
|---|---|
| Документация | Ссылки, согласованность терминов/статусов/ID; review второго |
| Contract | Валидные/невалидные fixtures, producer/consumer совместимость |
| Gameplay | Применимые offline-проверки и run игрового smoke-сценария |
| Анализ | Sample input, повторяемый расчёт и сверка с исходными данными |
| ML | Frozen config/data split, baseline-сравнение, бюджет и EVALUATION |

Исправление бага проверяется на воспроизводящем его случае. Если проверка невозможна, записать причину и необходимые действия; это не успешный результат. Долгие train/game runs выполняются в согласованном бюджете задачи.

## PR и завершение

Использовать [PR template](.github/PULL_REQUEST_TEMPLATE.md), связать T-ID и Issue при наличии, приложить фактические проверки. Не использовать автоматическое `Closes` до готовности всех AC. Второй человек проверяет и вливает. После merge обновить реестр, при необходимости STATUS и handoff. Полный DoD — в TEAM_WORKFLOW.

Для ошибки создать [bug report](.github/ISSUE_TEMPLATE/bug_report.md), для архитектурного выбора — [decision request](.github/ISSUE_TEMPLATE/decision.md) и Proposed ADR. Не объявлять личную идею принятым решением команды.

## Лицензия

До решения T001 лицензия собственного проекта не выбрана. Не добавлять чужую лицензию как собственную и не заявлять open-source статус только из-за публичного GitHub. Если после аудита есть внешние компоненты, документировать их отдельно. Это пункт организации репозитория, а не разрешение на перенос материалов.
